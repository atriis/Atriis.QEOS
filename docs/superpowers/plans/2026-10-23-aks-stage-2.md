# AKS Stage 2 (hardening and monitoring) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** QEOS on AKS gets NetworkPolicies for every workload, a checked restricted security posture, the same alerts and
five Grafana dashboards as Compose (kube-prometheus-stack underneath), Grafana trusted by a header secret instead of an
IP, and Container Insights logs.

**Architecture:** kube-prometheus-stack is a separate Helm release (`qeos-monitoring` in namespace `qeos-monitoring`),
installed by a cluster admin with `deploy/monitoring/install.sh`, because it needs CRDs and cluster roles that the
namespace-scoped deploy identity (ADR-038 ruling 9) cannot create. It provides the operator, Prometheus,
kube-state-metrics, node-exporter and its default Kubernetes/node rules; its own Grafana and Alertmanager are off. The QEOS
chart (deployed by `deploy-aks.yml` as today) adds, with `monitoring.enabled`: ServiceMonitors, PrometheusRules built from
the repository's rule files, postgres-exporter, an Alertmanager that renders its config with the existing
`monitoring/alertmanager/render.sh`, and Grafana with the proxy sidecar. Everything QEOS-specific therefore deploys with the
app, uses the existing Key Vault pattern, and stays inside the `qeos` namespace's NetworkPolicies.

**Tech Stack:** Helm 3, kube-prometheus-stack (prometheus-operator CRDs), nginx-unprivileged, Grafana 12.0.2,
Alertmanager v0.28.1, postgres-exporter v0.17.1, kind v0.33 (kindnet enforces NetworkPolicies), Bicep (AKS `omsagent`
add-on, data collection rule), promtool, bash.

**Spec:** `docs/superpowers/specs/2026-10-21-aks-deployment-design.md` (sections 5.3, 5.7, 5.11 item 2). Stage 1 record:
ADR-038 in `docs/adr/` (whatever its file name is; `grep -rl "ADR-038" docs`), `deploy/helm/README.md`,
`deploy/azure/README.md`.

## Global Constraints

- The Compose stack (dev, CI, single VM) behaves exactly as before; `bash monitoring/check.sh`, the gateway template tests
  and every CI job stay green.
- No secret in a values file, ConfigMap, image or log line. New Key Vault keys: `grafana-admin-password`,
  `grafana-proxy-key`, `monitoring-db-password` (required with monitoring on); `alert-slack-webhook-url`,
  `alert-teams-webhook-url` (optional, listed in `secrets.optional`).
- Every container the chart renders: `runAsNonRoot: true`, `readOnlyRootFilesystem: true`,
  `allowPrivilegeEscalation: false`, capabilities drop `ALL`, `seccompProfile: RuntimeDefault` (pod or container level).
- Third-party images pinned exactly as Compose pins them: `grafana/grafana:12.0.2`, `prom/alertmanager:v0.28.1`,
  `quay.io/prometheuscommunity/postgres-exporter:v0.17.1`; the sidecar uses the gateway's nginx-unprivileged image and
  digest (`gateway/Dockerfile`). The kube-prometheus-stack chart is pinned to one exact version, at least two weeks old
  at implementation time, in `deploy/monitoring/install.sh`.
- Prometheus `job` labels stay `auth`, `organization`, `project`, `ingestion`, `test-management`, `postgres`; the
  ingestion scrape keeps `honor_labels: true`.
- Header name `X-QEOS-Grafana-Key`, gateway env `GRAFANA_PROXY_KEY`; a set key matches `[A-Za-z0-9_-]{32,128}`. Empty
  (Compose) means the gateway sends no such header.
- Monitoring namespace default `qeos-monitoring`; kube-prometheus-stack release name `qeos-monitoring` with
  `fullnameOverride: qeos-monitoring`, so the Prometheus Service is `qeos-monitoring-prometheus` on port 9090.
- Service names inside the `qeos` namespace equal Compose's: `grafana` (port 3000), `alertmanager` (9093),
  `postgres-exporter` (9187).
- Git: commit with `git commit -o <own paths>` only; never `git add -A`, `git reset`, `git stash`; implementers never
  push. Each commit updates every `.md` its behaviour change affects. Trailer:
  `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.
- Local kind/compose runs: kind cluster `qeos-kind` (deleted afterwards), image tag `kind`; never touch compose project
  `qeos`.

## Review Focus

1. Kubelet probes or the edge's own traffic blocked by a default-deny policy: pods never become Ready. Expect: the
   default deny selects only this release's pods (`app.kubernetes.io/instance`), never the add-on's edge pods; the kind
   install with policies on is the test (Tasks 2, 5).
2. `monitoring.enabled` on a cluster without kube-prometheus-stack: expect a clear `helm` failure naming
   `deploy/monitoring/install.sh`, not a half-applied release. Test in Task 5's render test.
3. A forged `X-QEOS-Grafana-Key` or `X-QEOS-User-Email` from a client: the gateway overwrites both; a direct call to
   Grafana's Service without the key gets 403; another pod in the namespace cannot reach Grafana at all. Tests in Tasks 3
   and 6.
4. No alert channel configured (no webhook secrets, no `monitoring.alertEmailTo`): Alertmanager still starts with the
   null receiver and Watchdog is visible in it. Test in Task 5's kind check.
5. The `container` relabel breaking Compose: the restart alert and three panels must still see Compose containers.
   Tests: promtool unit test with a Compose-shaped series (Task 1); the namespace enforcement must keep the ingestion
   job's `honor_labels` (Task 5 checks the generated Prometheus config).

## Rulings in this plan (for the user to check)

1. kube-prometheus-stack is installed by a cluster admin with a script, not by `deploy-aks.yml`: the deploy identity
   is namespace-scoped by design. No new cluster-admin identity in GitHub.
2. Grafana and Alertmanager run from the QEOS chart, not from kube-prometheus-stack, so they reuse Compose's settings,
   `render.sh` and the Key Vault pattern, and sit inside the QEOS namespace's policies. The spec's "Grafana's Service
   from kube-prometheus-stack" becomes the QEOS chart's `grafana` Service.
3. NetworkPolicies are ingress-only; egress restriction waits for FQDN policies.
4. On AKS the QEOS namespace starts at PSA `enforce=baseline` with `restricted` warnings, because the add-on's edge
   pods share the namespace; kind enforces `restricted` on every push.
5. Rule and dashboard files are copied into the chart (Helm cannot read outside it) with a byte-equality test.
6. Node disk and memory alerts on AKS come from kube-prometheus-stack's default rules, not from `qeos-host`.
7. Noisy default rules are off (Task 4); the rest reach QEOS's Alertmanager and its channels.
8. The workspace cap is 5 GB/day in staging, not lower: it is shared with Defender.
